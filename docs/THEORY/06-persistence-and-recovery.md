# 06 — Persistence, Replay, and Recovery

**Chapter type:** persistence theory and implementation orientation  
**Evidence scope:** Foundry `development` local JSONL task, incident, repair-attempt, and HeadlessAi turn journals. Guarantees are described per store; no distributed persistence claim is made.

## 01 — Persistence is a recovery contract

Writing data to disk is not, by itself, a recovery strategy. A useful persistence design must answer:

- What is the durable unit: an event, a snapshot, or a complete request/result?
- How is a new record related to the previous durable state?
- What must be checked before replayed data becomes authoritative?
- What happens when a write fails after memory has already changed?
- What consistency boundary exists between two separate journals?
- Which process or host owns the lock?

Foundry currently uses local append-only JSON Lines (JSONL) journals for several work domains. Each record is a complete JSON value on one line. Stores preserve prior records and append new state rather than rewriting the entire file.

The format is intentionally inspectable. But inspectability is not integrity, and a local file is not a distributed database.

## 02 — Snapshots and event history

The task store writes complete `WorkTaskSnapshot` values. A newly created task must begin as an untouched `Queued` snapshot: no events, no lease, and no attempts. Each subsequent append must add exactly one event, preserve the complete prior event prefix, and retain the original task request/provenance.

On replay, the store validates each snapshot and reconstructs the latest snapshot for every task. It rejects empty records, invalid snapshots, a task that does not begin in the queued state, discontinuous event history, and changes to immutable task provenance.

This design makes each appended snapshot a recovery point while retaining the event history needed to explain the lifecycle. It is not a pure event-sourcing implementation: the journal stores snapshots containing the accumulated event list, not only individual domain events.

## 03 — Separate journals for separate responsibilities

Foundry has distinct local journals because the records have different lifecycle and validation rules.

| Journal | Durable record | Replay / consistency responsibility |
|---|---|---|
| `JsonlWorkTaskStore` | Complete task snapshots | Validate snapshot and event-prefix continuity; retain latest task state |
| `JsonlCodeRedIncidentStore` | Incident snapshots | Validate stable incident identity, monotonic sequence, update/clear rules |
| `JsonlWorkTaskRepairAttemptJournal` | Exact CI attempt projections | Validate schema, attempt order, run/attempt uniqueness, task identity, and terminal success |
| `JsonlHeadlessAiTurnJournal` | Model-turn reservation/result records | Preserve at-most-once invocation decisions and durable turn outcomes |

Each journal has its own lock and replay rules. That separation prevents unrelated records from being conflated, but it also means two files do not become one atomic transaction merely because a coordinator calls both.

For example, a repair-attempt record can be durably appended before the corresponding task snapshot is persisted. A crash between those operations can leave an orphan attempt record. Recovery must reconcile that state; it must not pretend that the two appends committed atomically.

## 04 — Replay is validation, not blind deserialization

A journal is an input boundary. Its bytes may be truncated, manually edited, generated by an older version, or corrupted by storage failure. Replay must validate domain invariants before accepting a record.

The task journal checks snapshot validity, event sequence, allowed lifecycle edges, timestamps, attempt bounds, lease identity, and immutable request provenance. The incident journal checks sequence progression, stable identity, active/update/clear transitions, and preservation of incident evidence. The repair-attempt journal additionally rejects a torn final line, discontinuous attempt numbering, reused CI run attempts, and new attempts after success.

A parser that successfully deserializes JSON has proved only that the bytes can be represented by the expected data shape. Domain validation determines whether the record is acceptable as history.

## 05 — Persistent coordinator and fail-closed behavior

`PersistentWorkTaskCoordinator` restores task snapshots into a new `WorkTaskCoordinator` during construction. For each mutation, it:

1. checks that the persistence adapter has not previously failed;
2. asks the in-memory coordinator to validate and apply the transition;
3. appends the resulting complete snapshot to the task journal;
4. returns the snapshot only after the append succeeds.

There is an important failure window: the in-memory coordinator may already have changed when the disk append fails. The adapter therefore records the persistence failure and permanently rejects further task operations in that process. The safe recovery action is restart and restore from the durable journal before dispatch resumes.

This is fail-closed process behavior, not a rollback. The implementation does not claim that memory and disk are transactionally atomic.

For repair decisions, the persistent coordinator requires an injected repair-attempt journal. It reads the immutable history under the journal's lock, requires the current attempt to equal the latest durable record, evaluates the decision, and persists the resulting task snapshot before returning. The two journals still have a crash-reconciliation boundary.

## 06 — Incident recovery and serialization

The CODE RED incident journal preserves a versioned, credential-free incident record. Creation starts at sequence one. Updates preserve immutable incident identity and advance the sequence. Clearing is explicit, advances the sequence, records the clear time, and prevents later updates.

`PersistentCodeRedRecoveryCoordinator` composes the incident store and persistent task coordinator. It selects the latest active incident while holding the incident store's in-process gate, then performs the task recovery operation before releasing that gate. This prevents a local update or clear from changing the selected incident sequence between selection and recovery receipt consumption.

That guarantee is intentionally narrow: it applies to one store instance in one process. It is not a cross-process lock, distributed transaction, or atomic commit across the incident and task journals.

## 07 — The guarantee boundary

The current local stores provide useful restart recovery on the same host when their files remain intact and their replay validation succeeds. They do not provide:

- cross-process or distributed locking;
- a shared authoritative task store across multiple Foundry instances;
- consensus or leader election;
- atomic transactions across task, incident, repair-attempt, and model-turn journals;
- automatic reconciliation of every possible orphaned cross-journal record;
- protection against an administrator or process with filesystem access rewriting journal contents;
- remote backup, replication, retention, or disaster recovery.

A single-process lock protects concurrent calls through one object instance. It does not protect a second instance opened against the same file. Production multi-host scheduling requires a storage and concurrency design whose atomic claim, fencing, durability, and recovery semantics are explicit.

## Questions for the reader

1. Why does the task journal append complete snapshots instead of rewriting the latest state in place?
2. What does replay validation establish beyond successful JSON deserialization?
3. Why does the persistent coordinator fail closed after a journal write failure instead of continuing with memory-only state?
4. What orphan state can occur when two journals are updated separately?
5. Why does an in-process lock not provide distributed lease arbitration?
6. What additional guarantees would a multi-host Foundry deployment require from its persistence layer?

## Exercise

Assume a repair attempt is appended successfully, but the process crashes before the corresponding task snapshot is written.

On restart, the repair-attempt journal contains the new record while the task snapshot still reflects the previous state.

Describe:
- which records are durable;
- why the task and attempt journals cannot be treated as one transaction;
- which checks should run before another repair is dispatched;
- why silently dropping the attempt would destroy evidence;
- what a future reconciliation operation should report before resuming work.

Then repeat the exercise with two Foundry processes attempting to claim the same task from separate store instances. Identify why the current single-process locks are insufficient.
